## 0. 背景と目的

現行版（v1、`index.html` 単一ファイル）は、端末の全データを 6 桁コードのルームに丸ごと PUT する同期方式で、次の問題がある。

1. 同期はページを開いた瞬間の 1 回だけ。開いている間の他人の変更が見えず、自分の保存で他人の追加を巻き戻す（後書き勝ち・全置換）
2. 同期の単位が「端末の全データ」なので、参加者の無関係なグループまでルームに混ざる
3. 通信失敗（401 等）を握りつぶして「接続済み」と表示する。失敗時も roomCode を保存し、その後の保存でルームを上書きする
4. 清算は送金リストを表示するだけで記録が残らない。締めた後の追加分だけを計算できない

v2 では、**グループ単位の共有・Google ログイン・リアルタイムかつレコード単位の同期・清算のイベント化** の 4 点を実現する。

## 2. 技術方針

- ビルド無しの静的ファイル構成を維持。**v2 では単一ファイルをやめ**、新コードは `js/*.js`・`css/*.css` の新規ファイルに置く（開発ルール B-1/B-3 の読み替え、2026-09-23 決定）。`index.html` は v1 のインライン `<script>` を撤去して `<script src>` を並べる器になる。純粋ロジック（按分・残高・清算）は `js/calc.js` に分離し `tests/calc.test.js` で固定する
- Firebase JS SDK **compat 版** を CDN（gstatic）から `<script>` で読み込む: `firebase-app-compat`, `firebase-auth-compat`, `firebase-database-compat`
- 認証: Firebase Authentication / Google プロバイダ。`signInWithPopup` を基本、失敗時（ポップアップ拒否・モバイル）は `signInWithRedirect` にフォールバック
- DB: Realtime Database（既存 `kinsen-kanri-default-rtdb`）。リスナー（`on('value')` または child 系）で即時反映。書き込みは変更したノードのみ（`set` / `update` / `remove`）
- SheetJS 取込・CSV 出力・清算アルゴリズム（貪欲法）・残高計算は v1 のロジックを流用してよい
- 既存 UI のトーン（配色・カード・モーダル）は維持。スマホ幅を最優先

## 3. データモデル（Firebase）

```
users/{uid}
  profile: { displayName, photoURL, updatedAt }
  groups/{code}: { joinedAt, order? }         ← 左サイドバーの一覧の元（order は並び順、工事5）

groups/{code}
  meta: { name, createdAt, createdBy(uid), schemaVersion: 2 }
  members/{mid}: { name, order, uid? }        ← uid は任意（「これは自分」紐づけ、v2.1 以降）
  payments/{pid}: {
    date(YYYY-MM-DD), memo, payerId(mid), amount(整数円),
    participants: { mid: true, ... },
    settlementId: null | sid,                 ← 清算済みなら sid
    createdBy(uid), createdAt, updatedAt
  }
  settlements/{sid}: {
    createdAt, createdBy(uid),
    transfers/{tid}: { from(mid), to(mid), amount, done(bool), doneAt? , doneBy? },
    paymentIds: { pid: true, ... }
  }
```

- `code` は 6 桁英数大文字（v1 と同じ生成規則）。既存の `Y39EN6` を「広島旅行」のコードとして引き継ぐ
- 配列は使わない（すべて ID キーのオブジェクト）。並び順は `date` と `createdAt` で決める
- 金額は整数円。按分の端数は v1 と同じ（表示時に丸め、残高は浮動で持ち、清算時に四捨五入）

**サイドバーの並び順（工事5）**: 並び順は人ごとの好みなので `users/{uid}/groups/{code}/order`（数値）に持ち、`groups/{code}` 側には何も書かない（他のメンバーには影響しない）。表示順のキーは「`order` が数値なら `order`、無ければ `joinedAt`（それも無ければ 0）」の昇順で、同点はコードの文字列順（`order` が文字列や null のときは無いものとして扱う）。`order` の無い既存グループはバックフィルせず、並べるときだけ `joinedAt` を使う。新規作成とコード参加は `order` =「今の自分の一覧の表示順キーの最大 + 1」（空なら 0）で書くので必ず一番下に入る（旧データの移行で入るグループは `order` 無し＝`joinedAt` 順）。つまみのドラッグ＆ドロップで並びが確定したら、その表示順で全グループに `order` = 0, 1, 2, … を `users/{uid}/groups` への 1 回の update（キーは `<code>/order`）で書き、`joinedAt` には触れない。`users/{uid}` は本人しか読み書きしないので、セキュリティルール（§4）は変更しない。実装は `js/group_order.js`（`sortCodes` / `nextOrder` / `attach`、並べ替えは SortableJS）と `js/store.js` の `setGroupOrder`

## 4. Firebase セキュリティルール（案 — 花井がコンソールで適用）

```json
{
  "rules": {
    "users": {
      "$uid": { ".read": "auth != null && auth.uid == $uid",
                ".write": "auth != null && auth.uid == $uid" }
    },
    "groups": {
      "$code": {
        ".read":  "auth != null && root.child('users/' + auth.uid + '/groups/' + $code).exists()",
        ".write": "auth != null && root.child('users/' + auth.uid + '/groups/' + $code).exists()",
        "meta": { ".read": "auth != null" }
      }
    },
    "rooms": {
      "$roomCode": { ".read": "auth != null", ".write": false }
    }
  }
}
```

- 参加フロー: ① `groups/{code}/meta` を読んで存在確認・グループ名表示 → ② `users/{uid}/groups/{code}` に自分を登録 → ③ 以降グループ本体を読み書き
- 旧 `rooms` は読み取りのみ（移行元）。旧クライアントの書き込みは失敗するが、旧クライアントは端末内では動き続ける（データは消えない）
- **開発中（v1 が本番稼働している間）のルール**: 上の `users` / `groups` を追加し、`rooms` だけは v1 のまま `".read": true, ".write": true` を維持する。`rooms` を読み取り専用にするのは本番切替（§8）のとき
- 実装役はルールの最終案を報告書に記載し、花井が適用する

## 5. 画面と機能

### 5.1 ログイン
- 未ログイン時はログイン画面のみ（「Google でログイン」ボタン、説明文）
- Discord / LINE 等のアプリ内ブラウザでは Google ログインが拒否されるため、UA からアプリ内ブラウザと判定できる場合は「Safari または Chrome で開いてください」と URL コピー用ボタンを表示
- ヘッダ右に表示名・アイコン・ログアウト。旧「☁ 同期設定」バッジは廃止し、接続状態インジケータ（接続中／オフライン／エラー）に置き換える

### 5.2 グループ一覧（左サイドバー）
- `users/{uid}/groups` に登録されたグループを、自分で決めた並び順（§3 の order。無ければ joinedAt 順）で一覧。新しく作った・参加したグループは一番下に入る。各行の右端のつまみ（⋮⋮）をドラッグして並べ替えられ、その順は自分のアカウントだけに保存される（他のメンバーには影響しない）。リアルタイム更新
- 「＋ グループを作成」: 名前とメンバー（2 人以上）→ `groups/{code}` を作り自分を登録
- 「コードで参加」: コード入力 → `meta` を読んで「『広島旅行』に参加しますか？」確認 → 参加。存在しないコードは明示エラー
- グループ設定に「共有コード」表示（タップでコピー）、「このグループから退出」（自分の一覧から外すだけ。データは残る）、「グループを削除」（メンバー全員に影響する旨の確認ダイアログ）

### 5.3 支払い
- v1 と同じ入力項目（日付・メモ・支払った人・金額・割り勘対象）。保存は `payments/{pid}` への `set`
- 履歴はリアルタイム反映。他人の追加が入った行は 1〜2 秒ハイライトしてよい
- `settlementId` が入っている支払いは薄いグレー表示、編集・削除ボタン無効（ツールチップ「清算済み」）
- 各行に小さく `createdBy` の表示名（誰が入力したか）を出す

#### 5.3.1 金額確認中の支払い（工事 3）
- 入力モーダルに「金額確認中」チェックボックス。☑ のときは金額が未入力または 0 でも登録できる（☐ のときは v1 と同じく 1 円以上必須）
- データ: `pending: true`、`amount` は 0 または null
- 履歴では**薄黄色**の背景で表示し、金額欄には「確認中」と出す。残高計算・清算計算からは除外
- 清算画面: 確認中の支払いが 1 件以上あれば、件数と一覧を警告として表示し、「この内容で清算する」ボタンを無効化する（暫定の送金リストは閲覧できる）
- 金額を入れて ☑ を外せば通常の支払いに戻る。編集モーダルで切り替え可
- 用途: 項目は思い出したが金額は他メンバーに確認が要る、という備忘録

### 5.4 残高カード
- 既定は **未清算分**（`settlementId == null` の支払いのみ）で計算
- 「累計を見る」トグルで全期間表示に切替

### 5.5 清算（新仕様）
- 「清算」ボタン → 未清算分の送金リスト（v1 の貪欲法）を表示
- 「この内容で清算する」ボタン → `settlements/{sid}` を作成し、対象支払い全件の `settlementId` に sid を書く（複数ノードを `update` で一括更新）
- 未清算の支払いが 0 件、または送金が 0 件（貸し借りなし）のときは確定ボタンを出さず、その旨を表示
- 送金 1 件ごとにチェックボックス（`done`）。全部 ☑ で「完了」バッジ
- 「過去の清算」一覧: 日付、送金リストとチェック状態、対象件数。各清算に「この清算を取り消す」
  - 取り消し: 対象支払いの `settlementId` を null に戻し、`settlements/{sid}` を削除。`done` が 1 つでもあれば確認ダイアログ
- 取り消しできるのは **最新の清算のみ**（古い清算を取り消すと計算順が崩れるため）。古いものはグレーアウトして理由を表示

### 5.6 取込・出力
- CSV 出力・xlsx/CSV 取込は v1 相当を維持。取込で作られる支払いは `createdBy` = 取込した人
- CSV 出力に「清算状態」列を追加

### 5.7 接続状態とエラー
- `.info/connected` を監視し、オフライン時はインジケータを灰色に。書き込みは SDK が再接続時に送る
- 権限エラー・認証切れは握りつぶさず、トースト等で明示

## 6. 移行（v1 → v2）

- **旧 `rooms/{code}` からの移行はコードで参加したときに 1 回だけ**行う:
  1. `groups/{code}` が存在しない、かつ `rooms/{code}` が存在する
  2. 旧ルームの `groups[]` のうち **先頭 1 件** をこの `code` のグループとして変換（members 配列 → `members/{mid}`、payments 配列 → `payments/{pid}`、`participants` 配列 → オブジェクト、`settlementId: null`、`createdBy: 移行実行者`）。2 件目以降のグループがあれば新しいコードを発行して同様に変換し、移行実行者の一覧に追加する
  3. 変換後、旧ルームには書き込まない（ルールでも禁止）
- 端末の localStorage `warikancho_v1` からの移行は **行わない**（v1 ユーザーは全員ルームに上げ済みの想定）。将来必要なら別工事
- v2 が使う localStorage キーは `kk_v2_*` の接頭辞（最後に開いたグループ ID 等の UI 状態のみ）

## 7.5 認証まわりの実地知見（工事 1 / 1-2 で確定、2026-09-23）

- iOS Safari では `authDomain = kinsen-kanri.firebaseapp.com` のままだと `signInWithRedirect` が `missing initial state` で失敗する（別サイト扱いのストレージ分離）。対策として `vercel.json` の rewrites で `/__/auth/*` と `/__/firebase/*` を firebaseapp.com へ転送し、`*.vercel.app` では `authDomain` を自ホストにする（`js/firebase-init.js` の `pickAuthDomain`）
- 自ホストを `authDomain` にすると、Google Cloud の OAuth クライアント（Web client (auto created by Google Service)）に **承認済みのリダイレクト URI** `https://<ホスト>/__/auth/handler` と **承認済みの JavaScript 生成元** `https://<ホスト>` を追加しないと `redirect_uri_mismatch` になる。プレビュー用と本番用（`kinsen-kanri.vercel.app`）は 2026-09-23 に登録済み
- Firebase Authentication の承認済みドメインにも同じホストが要る。プレビューはブランチ固定 URL `kinsen-kanri-git-v2-o-ka-s-projects.vercel.app` を標準とし、登録は 1 回で済ませる
- Vercel の Deployment Protection（Vercel Authentication）はオフにしてある（プレビューをスマホで開くため）
- 独自ドメインを将来当てる場合は、`pickAuthDomain` の判定・Firebase 承認済みドメイン・GCP のリダイレクト URI の 3 か所に追加が必要
