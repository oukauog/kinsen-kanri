## 3. store.test.js の作り

### 偽の Firebase（テストファイルの中だけで完結。ui_smoke_fakes.js は使っていません）

`KKFirebase` の中身:
- `ready: true`、`error: null`
- `auth.currentUser`: 基本は `{ uid: 'U1', displayName: 'テスト太郎', email: 'taro@example.com' }`。テストの中で displayName を空にしたもの、email も空にしたもの、null に差し替えます
- `now()`: 目印の文字列 `'__SERVER_TIMESTAMP__'` を返します
- `db.ref(path)` が返す偽の ref:
  - `set` / `update` / `remove`: `state.writes` に `{ op, path, value }` を記録して `Promise.resolve()`。`state.fail[path]` に err が置いてあれば、その path への set / update / remove は記録した後にその err で reject します
  - `once('value')`: `state.seed` から値を引いて、`val()` / `exists()` を持つ偽スナップショットで解決します。ぴったりの path が無ければ、いちばん近い祖先の path に置いた値の中をたどります（例: `groups/G1/payments/p1` に支払いを置くと、`…/p1/settlementId` の読み取りにも答える）
  - `push()`: キーが `P1`, `P2`, … と増える偽の ref を返します
  - `transaction(fn)`: seed の値に fn を適用します。fn が undefined を返せば `{ committed: false, snapshot }`、そうでなければ値を書いて `{ committed: true, snapshot }` で解決します
  - `on` / `off`: 記録するだけです
- 値の記録は undefined のキーも残す自前の深いコピーで行います。JSON のコピーだと、キーの過不足が見えなくなるためです
- 各テストの前に、writes・seed・fail・監視の記録・push の番号を空に戻します。あわせて `ready: true`、`currentUser` を基本の人、`onWriteError(null)` に戻します

### window の用意のしかた

store.js は末尾が `})(window);` なので、require の前に次の 2 つを用意します。
- `global.KKFirebase = 偽の Firebase`
- `global.window = global`

`require('../js/store.js')` の後は `global.KKStore` を使います。

store.js は読み込んだ時点の `KKFirebase` を変数 `FB` に掴みます。そのため、テストの途中で KKFirebase を別のオブジェクトに入れ替えると効きません。同じオブジェクトの `ready` / `auth.currentUser` を書き換えて状態を切り替えています。

### テストの進め方

`test(name, fn)` は登録だけです。fn は Promise を返してよく、最後に全部を順番に `await` して集計します。通過数と失敗一覧を出し、失敗があれば終了コード 1 です（既存の同期版の test とは混ぜず、このファイルの中で完結させています）。

失敗の確認用に `failure(fn)` を用意しました。同期の throw か Promise の reject かも区別して返します。

## 6. 気づいた点

**store.js を読んで気になった書き方**（直していません。テストは現状どおりに固定しています）
1. **ログイン切れ・未初期化は、reject ではなく同期の throw になる**
   - `uid()` と `ref()`（中の `requireReady`）は関数を呼んだその場で throw します。そのため、呼び出し側の `.catch(fail(...))` には届かず、トーストも出ません
   - また `uid()` は `ready: false` のときも currentUser を見ずに「ログインしていません」を投げます。Firebase の初期化に失敗した場合でも、uid を先に使う関数（leaveGroup・createGroup・addPayment など）は「ログインしていません」と表示されます
   - 画面側がログイン前の操作を出さないので実害は小さいと見ていますが、直すなら「関数の中を Promise で包んで reject にする」と「uid() の文言を分ける」です
2. **清算の createdAt だけが端末の時刻**
   - 支払い・グループの createdAt / updatedAt / joinedAt / doneAt は `FB.now()`（サーバ時刻）です
   - 清算の `createdAt` は `Settle.buildSettlement` が作る `Date.now()`（端末の時刻）を store.js がそのまま書いています
   - 過去の清算の並び順と「取り消せるのは最新だけ」の判定は createdAt で決まります。端末の時計が大きくずれていると、順番が入れ替わる可能性があります
3. **清算済みの確認と書き込みの間にすき間がある**
   - `ifNotSettled` は settlementId を 1 回読んでから別に書き込むので、アトミックではありません
   - 読んだ直後に他の端末で清算が確定すると、清算済みの支払いを書き換えられる時間が一瞬あります
4. **消えた支払いへの updatePayment は、中途半端な支払いを作る**
   - 支払いが他の端末で削除された直後に updatePayment が走ると、settlementId の読み取りは null（＝未清算）になって update が通ります
   - その結果、createdAt / createdBy の無い `payments/<pid>` ができます
5. **2 回に分けた書き込みが途中で切れると、片方だけ残る**
   - createGroup（users の set → groups の update）と deleteGroup（groups の remove → users の remove）は、ルールの都合で順番に 2 回書いています
   - 2 回目だけ失敗すると、自分の一覧に「本体の無いグループ」が残ります（画面では「（削除されたグループ）」になり、片付けられます）
6. **setGroupOrder は、一覧に無いコードを渡すと order だけのノードを作る**（Firebase の多パス update の性質）
   - 呼び出し側の ui.js（工事5）で、今の一覧にあるコードに絞っています。store.js 側には確認がありません
7. **removeMember は、そのメンバーが出てくる支払いには触らない**
   - 支払った人や割り勘対象に残った ID の扱いは、画面側（calc の正規化）に任されています

**固定できなかったもの・しなかったもの**
- migrateRoom / allocCodes / readRoom は依頼どおり対象外です。偽 Firebase の `transaction` は依頼どおり作りましたが、store.js で transaction を使うのは migrateRoom だけなので、今回のテストでは使われていません。次に migrateRoom を固定するときの下地です

- 共有コードの衝突時の再試行（findFreeCode の最大 10 回）は、乱数に依存するので固定していません
