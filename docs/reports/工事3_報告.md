## 4. 仕様からずらした点と理由

| # | ずらした点 | 理由 |
|---|---|---|
| 1 | `transfers/{tid}` に `fromName` / `toName`（清算時点の名前）も保存 | 仕様は `from` / `to`（mid）だけ。後でメンバー名を変えたり削除したりしても、**過去の清算が「誰から誰へ」だったか**が読めなくなるのを防ぐため。`from` / `to` は仕様どおり mid で持っています |
| 2 | 送金の ID を `t001` 形式（3 桁ゼロ埋め）にした | Firebase のキーは文字列順なので、`t1, t2, …, t10` だと `t1, t10, t2` の順に並ぶ。表示順が崩れないようにするため |
| 3 | 金額確認中の `amount` は **0 を保存**（仕様は「0 または null」） | `null` だと Firebase ではキー自体が消え、既存の支払いを確認中に切り替えたときに `amount` が無くなる。0 なら型が一定で扱いが楽。計算からは `pending` で外すので金額は使いません |
| 4 | 残高の「累計」でも**確認中は除外**する | 仕様 §5.3.1 の「残高計算・清算計算から除外」を優先。累計は「清算済みも含める」という意味に取りました（確認中は金額が未確定なので、どちらのモードでも足せない） |
| 5 | 清算済みの支払いは、編集ボタンを**押せる状態のまま**にして、押したら「清算済みの支払いは編集できません」とトーストを出す | `disabled` にすると理由が伝わらないため。見た目は薄く（`opacity: 0.35`）し、`title` に「清算済み」を入れています。データ層でも拒否しているので、押しても書き込まれません |
| 6 | 清算モーダルを開いている間、データが届くたびに中身を描き直す | 送金チェックを他端末とリアルタイムで共有するため（仕様の「リアルタイム反映」）。モーダルを開いたままでも最新の状態になります |
| 7 | 「この内容で清算する」の確認ダイアログに「記録すると編集・削除できなくなります（取り消しは可能）」を明記 | ロックの効果が事前に分かるように。仕様の文面には無い追記です |
| 8 | `tools/check_wiring.py` を修正（`ui.js` が動的に作る id を認識） | 工事3 で `settleConfirmBtn` を `ui.js` 側で作るようになり、既存の検査が誤検知したため |

## 6. 花井の検収手順（PC 2 ウィンドウ ＋ スマホ）

5. **清算確定**: 「清算」→ 確定ボタンが**有効**になっている → 対象件数と送金本数を確認 → 「この内容で清算する」→ 確認ダイアログ → OK

## 7. 要判断・申し送り

1. **確認中の支払いに「参加者」を選ばせているままでよいか**。金額が未定でも割り勘対象は選べる作りにしています（後で金額だけ入れれば済む）。入力を減らすなら、確認中のときは参加者選択を隠す案もあります
2. **2 端末で同時に清算を確定したとき**の扱い。今は後勝ちで、同じ支払いに後の sid が入り、先の清算レコードは「対象の支払いが他の清算に取られた状態」で残ります。実害は「過去の清算の対象件数が実態と合わない」程度ですが、気になるなら工事4 で `settlements` に transaction を入れるか、確定前に「他の人が清算していないか」を読み直す作りにできます（工事2 の移行と同じ考え方）
3. **清算済みの支払いを削除したい場合**の逃げ道。今は「清算を取り消す → 削除 → 再清算」の手順が要ります。頻度が高いようなら、清算済みでも削除だけは許す案（対象件数がずれるので非推奨）を検討します
4. **`settlements` が増え続ける**（自動削除しません）。数十件になっても表示は新しい順に全部出ます。多くなったら「直近 5 件だけ表示＋もっと見る」にする改修を工事4 で
5. **`doneBy`（誰がチェックしたか）は保存していますが表示していません**。「誰が入力したか表示」は工事4 の範囲なので、そこで一緒に出すのがよいと思います
6. **本番移行との順番**。工事2 の移行で入った支払いも `settlementId: null` なので、移行後にそのまま清算できます（工事2 報告の申し送りどおり、特別扱いは不要でした）
7. **Firebase ルールについて**（変更提案なし）。`settlements` は `groups/$code` 配下なので、既存のルール（自分の一覧に入っていれば読み書き可）でそのまま動く想定です。厳しくするなら `transfers/$tid/done` だけ全メンバー可・それ以外は作成者のみ、といった案が考えられますが、今の運用（友人グループ）では不要と判断しました
