# 00_開発ルール（相談役・実装役体制）— 金銭管理ツール版

- 原本: 花井の汎用ルール（実運用の事故と失敗から作られたもの）。2026-09-23 にこのプロジェクトへ持ち込み
- このファイルは「理由ごと守る」ための文書。実装役向けの要点は `CLAUDE.md` に転記する
- 末尾「§5 このプロジェクトでの読み替え」が金銭管理ツール固有の適用ルール

---

## 1. 体制 — AI を「二人」使う

- **相談役**（Cowork の Claude）: 花井と話し合い、やりたいことを整理し、仕様書と依頼文を書く。決定・失敗・ルールの記憶を持ち続ける「監督」
- **実装役**（Claude Code／ターミナル）: 仕様書を受け取ってコードを書く「職人」。工事ごとに使い捨てる

分ける理由:
1. 言語化の支援 — 「こういうものが欲しい」を正確な指示文にするのが最難関の工程。その翻訳を相談役が担う
2. 多視点＝検収の関門 — 書いた本人は自分のコードを疑えない。依頼者と実装者を分けると「実装計画の事前レビュー」「結果の検収」に他人の目が構造的に入る
3. 記憶の分離 — 相談役は長期記憶、実装役は使い捨て。1 セッションに詰め込むとコンテキストが満杯になり性能が落ちる
4. 紙（仕様書）が残る — 分業すると間に必ず文書が挟まり、暗黙知の文書化が強制される
5. 失敗の隔離 — 実装セッションが迷走したら捨てて作り直せる。相談役の文脈は無傷
6. コストの最適化 — 判断は高性能モデル、機械作業は軽いモデル。実装役を複数並行させ相談役が指揮もできる

## 2. 基本ループ

(1) 相談 → (2) 相談役が依頼文（＋大きい工事なら仕様書）を書く → (3) 花井が実装役に貼る → (4) 実装役の報告を相談役が読む → (5) 一緒に判定。OK なら次の工事、NG なら修正依頼文をもらって (3) へ

運用のコツ:
- スラッシュコマンドと依頼文は別々に貼れるよう分けて出す（まとめると後半が無視される事故が起きた）
- 一度にひとつの工事。依頼を欲張って束ねない（切り分けができなくなる）
- 最終判定は人間の目。テストが通っていても使い物にならないことがある
- **2026-09 以降の運用**: 実装役の報告はスクリーンショットではなく、実装役が `.md` ファイルとしてプロジェクトフォルダに保存し、相談役が直接読む（花井が貼る手間を省く）。依頼文に毎回そう書く

## 3. 守るルール（理由つき）

### A. 役割分担
- **A-1.** コードを書くのは実装役だけ。相談役はコードを書かない。理由: 直接いじるとレビューの関門が消え、記憶も汚れる。§1 の 1〜6 すべてが崩れる
- **A-2.** 仕様書は「生きた引継ぎ文書」として更新し続ける。理由: セッションはいつか消える。仕様書が最新なら誰でもどこからでも再開できる
- **A-3.** 実装役への依頼文には、起動コマンドを毎回コピペで添える。理由: 起動オプションの付け忘れは気づきにくく、作業が確認待ちで止まる。「毎回」をルール化すれば忘れようがない

### B. コードを壊さない
- **B-1.** テキスト置換型の編集（Edit ツール等）で既存コードを直接編集しない。編集はスクリプト（Python 等）経由で行い、編集後の構文チェックまで同じ流れで自動化する。理由: 置換型編集は「一致箇所の取り違え」からコードを丸ごと吹き飛ばす事故が実際に起きた。本質は「Python」ではなく「決定的で検証可能な編集手段」であること
- **B-2.** Git を退路にする。着手前に作業ツリーをきれいにしてコミット済みにし、工事ごとにブランチかコミットを切る。動いた状態には都度コミットを置く。理由: 「いつでも直前の動く状態に戻れる」ことが、AI に大胆な変更を任せられる唯一の根拠。着手前が汚れていると AI の変更と自分の変更が混ざって切り分け不能になる
- **B-3.** 新機能は「新規ファイル＋既存からの呼び出し」で足す。既存ファイルの改修は最小に。理由: 差分が新規ファイルだけなら、壊れても切り戻しが一瞬で、他の作業と衝突しない

### C. 品質と検収
- **C-1.** 回帰ゼロの原則: 既存の自動テストが全部通ること。新機能は OFF の状態で、改修前と同じ入力に対して同じ出力になること。テストが無い箇所を触るなら、触る前に現状の挙動を固定するテストを先に書かせる
- **C-2.** 直したバグは恒久テストで固定する。理由: 同じ壊し方をしたら必ずテストが落ちる状態にしておけば、バグは二度戻ってこない
- **C-3.** 「実装完了」と呼べるのは、利用者が画面から使える状態になってから。「機能完成（組込待ち）」と「実装完了」を言葉として区別する
- **C-4.** テストの通過は完成の証明ではない。最後は必ず花井が実物を触って判定する。相談役は判定前に「何を触って何を確認すれば良いか」の確認手順を出す
- **C-5.** 大きめの工事（複数ファイルにまたがる／挙動が変わる／後で理由を問われそうなもの）は、終わりに検証レポートを書かせる。小さい修正は不要

### D. 記憶と引継ぎ
- **D-1.** 決定・ルール・教訓は、その都度プロジェクトメモリに書く。内容は「決定とその理由」「試してダメだった案」「二度と踏みたくない失敗」。索引は 1 行 150 字以内の見出しに徹し、詳細は個別ファイルへ
- **D-2.** セッションは節目で畳む。畳む前に仕様書・レポート・メモリを最新化する。節目が近づいたら相談役から畳むタイミングを提案する

### E. 環境
- **E-1.** プロジェクトフォルダ直下に `CLAUDE.md`（実装役向けの常設ルール掲示板）を置く。B〜C の要点をここに書く。草案は相談役が作る

## 4. このプロジェクトの前提

- 作るもの: 金銭管理ツール（割り勘・貸し借り管理の Web アプリ）v2 再設計 — 詳細は `docs/10_仕様書_v2再設計.md`
- 使用言語・フレームワーク: HTML / CSS / JavaScript（ビルド無し）、Firebase（Realtime Database, Authentication）compat SDK を CDN 読込。テストは Node.js 標準機能のみ（フレームワーク無し）
- 実行環境: 利用者はスマホ（Safari / Chrome）と PC ブラウザ。ホスティングは Vercel（main → 本番 https://kinsen-kanri.vercel.app/、他ブランチ → プレビュー URL）。開発機は日本語 Windows（ユーザー owner）
- プロジェクトフォルダ／リポジトリ: `C:\Users\owner\Documents\GitHub\kinsen-kanri` ／ https://github.com/oukauog/kinsen-kanri
- 絶対に壊してはいけないもの: ①本番 `main`（友人グループが利用中）②Firebase 旧パス `rooms/{code}`（友人の実データ、特に Y39EN6）③利用者端末の localStorage `warikancho_v1` ④Firebase セキュリティルール（変更は花井のみ）
- 現時点の困りごと／最初にやりたいこと: 同期方式の全面見直し（グループ単位・Google ログイン・リアルタイム・レコード単位）と清算のイベント化。工事 1 から着手

## 5. このプロジェクトでの読み替え（2026-09-23 決定）

- **B-1 の具体**: 既存 `index.html` への変更は Python スクリプト（UTF-8 明示、read → 検証付き置換 → write）で行い、スクリプトは `tools/` に残す。置換前に一致箇所が「ちょうど 1 つ」であることをスクリプト内で検証し、違えば何もせず終了する。新規ファイルの作成は Python でも Write ツールでも可（新規は吹き飛ばす対象が無い）。編集後は `node --check` で JS 構文チェック、HTML は最低限タグ整合の目視
- **B-3 の具体**: v2 の新コードは新規ファイル（`js/*.js`、`css/*.css`）に置き、`index.html` への変更は「v1 のインライン `<script>` ブロックの撤去と `<script src>` の追加、DOM の最小変更」に限る。v1 の内容は Git 履歴にあるので複製は不要
- **C-1 の具体**: 現行に自動テストは無い。按分・残高・清算（貪欲法）の純粋ロジックを `js/calc.js` に切り出し、切り出す前に v1 の挙動を固定するテスト（`tests/calc.test.js`、`node tests/calc.test.js` で実行）を書く。検証用ケースは `docs/30_テストケース_清算.md`。UI の回帰は目視
- **C-5 の具体**: 各工事の終わりに `docs/reports/工事N_報告.md` を実装役が UTF-8 で保存する（検証レポート兼報告書）。項目は依頼文で毎回指定
- **A-3 の具体**: 起動コマンドは `claude --dangerously-skip-permissions`（`kinsen-kanri` フォルダで実行）。依頼文の冒頭に毎回記載
- **日本語 Windows の注意（依頼文に毎回記載）**: 日本語を `echo` やリダイレクトで書かない（cp932 で化ける）、.bat/.cmd を作らない、ファイルは UTF-8（BOM 無し）。コンソール表示の化けはファイルを読んで判定
- **本番との並行**: 工事はすべてブランチ `v2` 上。旧 `rooms/` は読みも書きもしない（読むのは工事 2 の移行実装のみ、書きは常に禁止）。動作確認のグループ名は「テスト〜」で始め、実在コードは使わない
- **適用しない項目**: なし（C-1 は上の読み替えで適用）
